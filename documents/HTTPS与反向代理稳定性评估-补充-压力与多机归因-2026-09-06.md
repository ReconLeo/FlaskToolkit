## 二、阶段 3A 并发压测

### 本机（127.0.0.1）压测（pc_stress.py，单线程模式）

| 场景 | 结果 | 延迟分布 |
|------|------|---------|
| mixed 100 并发 × 3 轮（300 请求） | 300 成功 0 错误 | p50 2249ms，p95 4216ms，rps 19.8 |
| login 50 并发 | 50 成功，**0 锁定误伤** | p50 2492ms |
| upload 10 并发 × 2MB 无效 zip | 10 全 400（校验拒绝，预期） | p50 229ms |

单线程（Werkzeug 默认）串行排队效应明显但**稳定无错**；并发登录未触发 ip_username 锁定误伤。

### threaded 对比（FT_THREADED=1 临时开关）

| 场景 | 结果 |
|------|------|
| mixed 100 并发 | **主服务端口 5010 丢失（假死）**，269/300 连接被强制关闭（F7） |
| login 50 并发 | 全部连接失败 |
| upload | 连接被拒 |

**F7（P1）**：Werkzeug dev server `threaded=True` 高并发下服务假死（主 socket 退出、跳转线程仍存活、进程未退出）。开发服务器线程模式不可用于并发承载；部署建议：保持默认单线程或切换生产 WSGI（Windows 建议 waitress、Linux gunicorn + TLS 由 Nginx 终止）。

### Android 真机压测（50 并发 × 3 轮 = 150 请求，单线程模式）

| 拓扑 | 结果 | 延迟 |
|------|------|------|
| 反代 https://8443 | 150/150 全 200 | p50 1137ms，p95 2085ms |
| 直连 http://5010 | 150/150 全 200（F10 修复后） | p50 1217ms，p95 2481ms |

F10 修复前直连拓扑登录态 API 全部 401（见第五节）。

## 三、阶段 3B 大文件压测（echo-upload 测试插件）

### 直连 HTTPS 链路（阶段 2 模式，10/50MB）

| 项 | 结果 |
|----|------|
| 10MB 上传/下载 | 200，sha256 与本地一致，下载回传一致 |
| 50MB 上传/下载 | 200，哈希一致 |
| 2×50MB 并发上传 | 200 ×2（单线程串行排队但成功） |
| 101MB | 413（MAX_CONTENT_LENGTH 兜底，预期） |

### 反代模式链路（Nginx 8443）

| 项 | 结果 |
|----|------|
| 50MB 上传/下载 | 200，2.3s/1.6s，哈希一致 |
| 100MB 上传 | 直连 http 200（route `max_upload:110` 突破全局 100MB 兜底，1.2s）；反代在 Nginx `client_max_body_size 100m` 时 413（F11），调整 110m 后 200（3.9s） |
| 100MB 真机上传 | 反代 200（9.3s）/ 直连 200（8.5s），**两拓扑 sha256 一致**（数据完整性） |

**F9（P3 语义）**：`MAX_UPLOAD_SIZE_MB` 限制的是**整个请求体**（含 multipart 包装），100MiB 文件 + 包装略超 100MB 会被 413；大文件路由须声明 `max_upload`（AirDrop GB 级路由同机制，permission.py 注入 `request.max_content_length`）。
**F11（P3 部署）**：反代链路大文件上限 = min(框架 route max_upload, Nginx `client_max_body_size`)；Nginx 默认 1MB、示例 100m，需按实际路由上限调整（本文验证 110m 承载 100MB 文件）。

## 五、阶段 4 多机 IP 归因复测（R6 闭环 ✅）

**F10（P1 回归，v4.12.0 引入，本评估发现并修复）**：`EXTERNAL_SCHEME=https` 使 `is_secure_cookie_mode()` 全局判定为 True → 内部 HTTP 直连（http://IP:5010）登录 cookie 也带 `Secure` → 客户端（requests/浏览器）按标准丢弃 → **登录态全部 401**（直连拓扑 probe/stress 全暴露）。修复（v4.12.1）：`is_secure_cookie_mode()` 改跟随**请求实际协议** `request.scheme`（ProxyFix 后反代场景为 https、内部 http 直连为 http），无请求上下文回退 `get_scheme()`；test_network J 组 41/41 兼容。修复验证：直连 http 登录 cookie 无 Secure（登录态 200）、反代 https 有 Secure（200）。

**归因比对**（审计日志插件禁用/启用事件，probe 触发）：

| 时间 | 拓扑 | audit ip |
|------|------|----------|
| 23:12:43-53 | 反代 / 直连 | 10.17.17.174 / 10.17.17.174 |
| 23:14:43-54 | 直连(direct) / 反代(proxy) | 10.17.17.174 / 10.17.17.174 |

结论：**直连拓扑 remote_addr 直读正确；反代拓扑 ProxyFix 正确归因 X-Forwarded-For**（未误归因到 Nginx/127.0.0.1）。R6（多机 IP 归因端到端）闭环。

## 七、部署建议（写入开发规范 3.4/部署章节）

1. **并发承载**：dev server 保持默认单线程（稳定），高并发场景切生产 WSGI（Windows: waitress；Linux: gunicorn + Nginx TLS 终止），勿用 dev server threaded 模式
2. **大文件**：大文件路由声明 `max_upload`；反代链路同步调大 Nginx `client_max_body_size`（≥ 路由上限）
3. **Cookie Secure**：v4.12.1 起自动跟随请求实际协议，http 直连与 https 反代均自动正确，无需手动配置（仍可显式强制）
4. **多机部署**：反代场景开启 `TRUST_PROXY_HEADERS=true`（审计 IP 归因/登录锁定维度依赖）；`EXTERNAL_SCHEME/EXTERNAL_PORT` 保证分享地址外部可达

## 八、结论

框架在**单线程 dev server** 下并发/大文件链路稳定（100 并发无错、100MB 上传哈希一致、双拓扑归因正确）；评估发现 1 项 P1 回归（F10，已修复并真机验证）与 4 项 P3 记录项；threaded 模式高并发不可用属 dev server 边界（部署建议解决）。长稳 12h 数据待用户回传后补录。
