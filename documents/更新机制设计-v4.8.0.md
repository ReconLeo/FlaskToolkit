# FlaskToolkit 版本检查与更新机制设计（v4.8.0）

> 设计目标：为框架提供"检查新版本 + 更新到新版本"的完整运维闭环，同时覆盖**有 Git / 无 Git（企业内网）两种部署形态**。
> 状态：设计稿 v1（2026-09-04）→ 已确认关键决策 → 待实施
> 版本规划：本设计拆两个版本落地——**v4.8.0 实施 F1（版本检查推送）+ F4 archive 后端 + 发布工具链**；git 后端在开源环境顺带支持。

## 〇、需求来源与已确认决策

**用户需求（请求 61）**：启动框架时检查新版本并推送（前端后台 + 后端 app.py 命令行显示，数据源默认 GitHub changelog.json，只存最新版本变化，用户可自定义推送数据源）；tools 实现版本更新脚本（拉取 → 删旧填新 → 保留用户配置）。

**已确认决策（2026-09-04）**：

| # | 决策点 | 结论 |
|---|--------|------|
| D1 | 更新包形态 | **默认精简运行包**（仅运行必需文件，包小更新快）；**全量包可选**（含 tests/documents/examples，供离线归档/完整审计）；**定制包**：企业可附加自定义目录/文件（内网私有插件、本地文档、配置模板等） |
| D2 | 完整性校验 | **sha256 必选 + 签名可选**：changelog.json 内置 sha256 必须比对；配置 `UPDATE_PUBLIC_KEY_PEM` 后强制验签（与插件包签名机制对齐） |
| D3 | 自动检查开关 | **可配 + 预设关闭**：`UPDATE_CHECK_ENABLED` 配置项；daily 默认开、strict/lan-open 预设默认关（内网无外网不空等） |
| D4 | 后台更新入口 | **仅展示 + 引导**：后台展示新版本信息/变更日志/下载链接，实际更新跑 `tools/update.py` 命令；不做一键更新按钮 |

## 一、F1：版本检查推送（只读，不负责更新）

### 1.1 数据源 changelog.json（仓库根目录）

只存**最新一个版本**的变化（用户需求），字段最小化：

```json
{
  "latest_version": "4.8.0",
  "published_at": "2026-09-04",
  "download_url": "https://github.com/ReconLeo/FlaskToolkit/releases/download/v4.8.0/FlaskToolkit-v4.8.0-runtime.zip",
  "sha256": "…",
  "signature": "…",
  "changes": [
    "版本检查与更新机制（F1/F4）：…",
    "…"
  ]
}
```

- 默认源：`https://raw.githubusercontent.com/ReconLeo/FlaskToolkit/main/changelog.json`
- 企业内网：`UPDATE_FEED_URL` 指向内网镜像（管理员同步该文件 + 更新包即可）
- `changes` 渲染到后台"版本更新"卡片与启动横幅下

### 1.2 core/update_checker.py

- `check_for_update(force=False) -> UpdateInfo | None`：拉取 changelog → 校验 sha256/签名（有配置时）→ 版本比较 → 返回结果
- **版本比较**：tuple 化（`4.8.0` → `(4,8,0)`）逐位比较，不引第三方依赖
- **异步惰性**：app 启动后后台线程检查（**3s 超时**，`socket.setdefaulttimeout`/requests timeout），网络失败静默（日志 warning），**不阻塞启动**
- **缓存**：`data/cache/update_check.json`（`{checked_at, latest_version, published_at, changes, sha256, ...}`），**24h TTL**（`UPDATE_CHECK_INTERVAL` 可配）
- 仅只读，不下载包、不触发更新（更新归 F4）

### 1.3 推送展示

| 位置 | 形态 |
|------|------|
| app.py 命令行 | 启动横幅下：有缓存 → "发现新版本 v4.8.0（变更 N 条，见 tools/update.py --help）" 或 "已是最新版本 v4.7.0"；无缓存 → 后台检查写缓存，本次启动不打印（避免阻塞） |
| 管理后台仪表盘 | "版本更新"卡片：当前版本 vs 最新版本、变更日志列表、下载链接、刷新按钮（`/api/admin/update/check`，admin 权限，force 刷新） |
| 系统管理页 | 关于卡片下方加"版本检查"行（当前/最新/检查时间） |

### 1.4 配置项（进 CONFIG_ITEMS + config CLI）

| 配置项 | kind | 默认 | 说明 |
|--------|------|------|------|
| `UPDATE_FEED_URL` | str | GitHub raw changelog.json | 更新数据源，内网可指向镜像 |
| `UPDATE_CHECK_ENABLED` | bool | True | 自动检查开关；**strict/lan-open 预设默认 False**（daily 默认 True） |
| `UPDATE_CHECK_INTERVAL` | int | 24 | 检查缓存 TTL（小时） |
| `UPDATE_PUBLIC_KEY_PEM` | path | '' | 配置后强制验签更新包（与插件包签名机制同思路） |

## 二、F4：版本更新脚本（双后端）

### 2.1 后端抽象

```
tools/update.py
  子命令：--check / --backup / --apply / --rollback / --dry-run
  后端选择：项目目录是 git 仓库 → git 后端（默认）；
           否则或 --backend archive → archive 后端（非 Git）
  输出：机器可读（--json 可选）+ 人类可读
```

两后端共享同一套 **用户数据路径清单**（见 2.4），保证"保留用户配置"语义一致。

### 2.2 git 后端（开源环境，已有方案确认）

`--check`（读 changelog 比较）→ `--apply`：`git fetch origin main` → `git stash push -u` → `git reset --hard origin/main` → `pip install -r requirements.txt` → `selfcheck` 失败自动回滚（`git reset --hard <备份commit>` + `git stash pop`）→ `--dry-run` 演练模式。

### 2.3 archive 后端（非 Git，企业内网主路径）

1. `--check`：读 `UPDATE_FEED_URL` changelog.json → 最新版本 + `download_url` + `sha256`
2. **下载**：zip 到 `temp/update_downloads/`（HTTPS 优先；内网 HTTP 打印风险提示，用户确认后继续）
3. **校验**（全部通过才继续）：
   - `sha256` 比对（必选，changelog 内）
   - 配置 `UPDATE_PUBLIC_KEY_PEM` 时强制验签（signature 字段）
   - zip slip 防护（复用上传链路检测逻辑）
   - zip 内 `manifest.json` 的 `version` 必须与 changelog `latest_version` 一致
4. **备份**：框架文件（清单见 2.4）打包 `data/backups/update_backup_<ts>.zip`（含当前 FRAMEWORK_VERSION 标记）
5. **替换**：解压覆盖框架文件，**显式跳过用户数据路径清单**（与 gitignore 语义对齐）
6. **验证**：`run_selfcheck()` 通过 → 成功；失败 → **自动回滚**（恢复备份）
7. 提示重启服务

### 2.4 用户数据路径清单（双后端共用，收敛唯一来源）

与 git 方案 gitignore 语义严格对齐，archive 解压时显式跳过：

```
data/            # 用户配置/统计/缓存（user_config.json、frontend_tools.json、backups、cache、audit.log…）
plugins/configs/ # 插件配置
plugins/data/    # 插件数据
plugins/temp/    # 插件临时
logs/
.plugin_cache/
workspace/
temp/            # 框架临时（更新下载包也放这里，替换时自然跳过）
```

**实现**：清单定义在 `tools/update.py` 单处（`USER_DATA_PATHS` 常量），git 后端以注释对齐 gitignore、archive 后端实际执行跳过；文档（开发规范/版本收尾-checklist）引用该常量，避免两份清单漂移。

### 2.5 安全边界

- 非 Git 更新本质是**执行发布者代码**——信任模型与插件一致：sha256 必须、签名可选
- 下载默认 HTTPS；内网 HTTP 需用户明确知晓风险
- 更新前记录当前版本完整性（selfcheck），更新后验证新版本
- `tools/update.py` 本身会被更新包覆盖——升级后以新版本脚本为准（发布流程保证 archive 包内含最新 update.py）

## 三、发布工具链（配套，非 Git 包生产）

新增 `tools/release.py`（维护者本地使用）：

- `--bump-version 4.8.0`：三处版本号同步（global_var/test_admin_api/README 双版徽章）→ 提示更新开发规范/Roadmap
- `--build-runtime`（**默认**）：按精简清单打包 `FlaskToolkit-<ver>-runtime.zip`（自动生成 zip 内 `manifest.json`：version/required_python/files）
- `--build-full`（可选）：全量包 `FlaskToolkit-<ver>-full.zip`（含 tests/documents/examples，供离线归档/完整审计）
- `--include <src>:<dest>`（可重复，定制包）：企业将内网私有插件、本地文档、配置模板等附加目录/文件打入包内——与 `--build-runtime` 或 `--build-full` 叠加，产物即定制包（审计意见：默认精简、全量可选、定制扩展）
- `--write-changelog`：生成/更新根目录 `changelog.json`（latest_version/published_at/download_url/sha256/signature/changes）
- `--sign`（可选）：用私钥对 zip 签名写入 changelog `signature`

发布流程：`release.py --bump-version` → 回归全过 → `--build-runtime`（或 `--build-full` / 叠加 `--include` 出定制包）→ `--sign`（可选）→ `--write-changelog` → git 提交 + GitHub Release 上传 zip + push changelog.json。

**定制包约定**：`--include <src>:<dest>` 的 `<dest>` 为包内相对路径（如 `plugins/enterprise_tool.py`、`documents/内网运维手册.md`）；更新时与框架文件同规则覆盖，但 2.4 用户数据路径清单（data/、plugins/configs/ 等）始终保留——企业私有插件建议随包发布至 `plugins/`，更新后不丢失。
